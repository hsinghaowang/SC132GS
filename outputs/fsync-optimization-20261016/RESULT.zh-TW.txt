FSYNC / RAW capture API 優化：板端結果（2026-10-16，Asia/Taipei）

結論
已整合至共用 gs130wi_capture library，RTSP 使用該 library 的新擷取實作。
最終部署是 --tone-map shared --hevc-profile main，輸出 HEVC Main 8-bit yuv420p。
Shared8 session 11 的 600.418 秒板端監測與兩個獨立 Windows RTSP 解碼窗口均通過；本窗口沒有重現 error=9。
目前保留測試版持續運行，未在測試結束後重啟相機。

實作
- packed RAW10 解包與全畫面 highlight count 合併，AArch64 NEON 每批16 pixels，保留 scalar fallback。
- 使用既有 decoded scratch；不新增整張 RAW 備份。
- 最後一次讀取 MMAP 後立即 QBUF，再做 HDR grid 統計、demosaic、median；RAII 保護短幀/例外歸還。
- 擷取 producer 與後處理 consumer 透過單槽 move handoff 交接 owning vectors，不靜默覆蓋同步幀。
- 每眼 V4L2 requested=8、actual=8；沒有加大相機 queue。
- 公開 C++17 Capture API 不變，RTSP 的後處理耗時計時保留在上層。

其他檢查
WSL 完整程式 build 與21項 CTest 通過；ASan/UBSan portable 8項通過。
AArch64 NEON QEMU portable 8項通過；NEON/ARM scalar/x86 scalar 結果 digest 相同。
板端原生 build 與 fused RAW、move handoff、實際 Device syscall fixture 三項通過。
fixture 在 QBUF 時覆寫 RAW mapping，仍得到正確輸出；短幀/ERROR buffer 歸還一次、QBUF failure 不 double return。
前一輪 Main10 正常停止的 common capture trace 有544筆成功 DQBUF/QBUF 配對、1088筆 statistics/render 均在 QBUF 之後；這只證明相同底層生命週期，不算 Shared8 的10分鐘解碼資料。
離線 ARM CPU2 benchmark 因頻率/排程造成跨輪時間差異很大，不使用它宣稱固定SIMD加速倍數。

限制與保留失敗證據
1. 本結果是有界600秒驗證，不代表長時間可靠性已通過，也無法反推所有歷史error=9的唯一根因。
2. Shared8 stereo 目前為未整流 cam0|cam1；depth 使用既有自身校正。原 stereo GPU rectification 只支援 Main10，這輪沒有帶入該選項。
3. 保留原必要的格式轉換、composition 及 depth submit 既有 copy；不是整條 pipeline 零拷貝。
4. 切換前原舊版 session6 已停止於 error=10、skipped=1，保存於 old-owner-fault；此發生於新版本部署前，不算新版本 error=9。
5. 第一次部署檢查誤讀尚未reset的舊session sticky error10，保存 deployment-attempt-01.json 並回復舊版；後續啟動檢查改成等待新session。
6. Main10初輪因後處理log binary缺漏而強制重編；Main10後輪因輸出規格更正為Shared8而中斷。它們均保留 partial result，不列為600秒通過。
